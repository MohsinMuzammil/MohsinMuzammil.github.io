Software Design

Three Musketeers Board Game

A Java implementation of the Three Musketeers board game, built across three phases: CLI, JavaFX GUI, and a team-based refactor focused on design patterns and SOLID.

October – December 2021 Java · Software Design · JavaFX

Overview

This project was a Java implementation of the Three Musketeers board game, developed across three phases:

  • Phase 1 — Command-line version. A fully playable version of the game in Java, controlled entirely through text input and output.
  • Phase 2 — GUI version. A graphical version built with JavaFX, adding visual rendering of the board, move selection, and game state.
  • Phase 3 — Team refactor. A collaborative pass over the codebase to improve structure by recognizing common design patterns and applying SOLID design principles.

The Game

Three Musketeers is an asymmetric board game with two players. The Guards win if they manage to get all three Musketeers onto the same row or column. The Musketeers win if they can no longer capture any Guards (i.e. they cannot move) and they are not all on the same row or column.

The game is playable in two modes:

  • Player vs. Player
  • Player vs. Computer — with both random and greedy strategies implemented

What I Learned

Completing this project gave me valuable experience with:

  • Designing heuristics for random and greedy strategies
  • The JUnit and JavaFX frameworks
  • Applying object-oriented programming and SOLID principles in Java
  • Recognizing and applying design patterns to simplify software
  • Git version control, including branching, merging, and pull requests
  • Coordinating and working within a team to develop software
  • Agile scrum methodologies, used by professional software teams

Reflections

This project was my first real introduction to software engineering as a discipline, rather than just programming. The three-phase structure made the point clearly: the same game can be implemented in wildly different ways, and much of the work of a software engineer is about choosing the right structure for the problem.

Phase 3 was the most valuable part. Working in a small team to refactor code we'd already written forced us to look at our own work critically, identify where our designs broke down, and apply patterns and principles we'd only seen in lectures. It was also my first experience with git branching and pull requests, and with agile workflows more broadly — tools and habits that I've relied on ever since.
