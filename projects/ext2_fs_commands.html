ext2 File System Commands

Implementing core file system commands in C against a real ext2-formatted virtual disk, with mutex-based synchronization.

November – December 2022 C · Operating Systems · File Systems

Overview

In this project, I learned how the ext2 file system works and implemented a set of core file system commands in C that operate directly on an ext2-formatted virtual disk. Rather than calling into an existing API, I worked with the raw on-disk structures: superblocks, inode tables, data blocks, and directory entries.

The commands I implemented were:

  • mkdir — creating a directory
  • cp — copying a file
  • rm — removing a file
  • ln_hl — creating a hard link
  • ln_sl — creating a symbolic link

Each command was implemented with mutual exclusion over shared file system structures, using mutexes to ensure that concurrent operations could not corrupt the disk image.

Working with Binary Data

Although these commands may seem simple on the surface, the reality of implementing them for a specific file system is quite involved. Everything has to be done at the level of binary data, and doing it correctly requires a solid understanding of how the file system organizes itself on disk.

In ext2, every file and every directory corresponds to an inode. Directories are not opaque containers — they are files whose data blocks hold a linked list of directory entries, each one mapping a name to an inode number. There is no library that abstracts this away; every lookup, every insert, and every deletion is something I had to perform myself.

A Concrete Example: rm

Consider the command rm /folder/myfile. In an ext2 file system, this is not a single operation but a sequence of careful steps:

  • Start at the root inode and search its data blocks — a linked list of directory entries — for an entry named folder.
  • Verify that the entry actually refers to a directory, not a file.
  • Search folder's data blocks for an entry named myfile, and verify that it refers to a regular file.
  • Once verified, mark the inode and the data blocks that hold myfile's contents as free, so they can be reallocated by other files or directories.
  • Finally, update the parent directory's data blocks to reflect that the entry myfile has been removed — either by unlinking it from the linked list or marking it as deleted.

Every one of these steps has to be done correctly, in the right order, and with the right locking. Skipping a step or performing them out of order would leave the disk in an inconsistent state.

Synchronization

Because multiple commands can act on the same file system structures at once, I used mutexes to guarantee mutual exclusion over the inode table, data block bitmap, and directory entries. This ensures that concurrent operations cannot corrupt the disk image, even when they touch overlapping regions of the file system.

Reflections

This project gave me a much deeper understanding of what a file system actually is. On the surface, commands like cp and rm feel trivial — you type them and something happens. But implementing them from first principles against raw disk structures made it clear how much careful bookkeeping is happening underneath.

It also strengthened my intuition for low-level systems programming in C: pointer arithmetic on binary data, reasoning about byte offsets, and synchronizing shared state. These are skills that only really develop when you have to do them, and this project gave me that opportunity.
