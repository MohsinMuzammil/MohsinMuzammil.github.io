Game Development

Meepo is You

Implementing the game logic for a puzzle game where the player rewrites the rules of the game by pushing blocks around the map.

February 2021 Python · pygame · pytest

Overview

Meepo is You is a puzzle game written in Python with a graphical user interface. The premise is inspired by games like Baba is You: the player moves around a map, pushing blocks that represent words, and by arranging those words into sentences they can create, modify, or break the rules of the game itself.

The GUI was provided to me as part of the assignment — my task was to implement the game logic. This meant designing the systems for movement, block pushing, rule parsing, and win conditions, and integrating them cleanly with a front-end I hadn't written.

Movement and Pushing

Every player input triggers a small set of checks: is the target tile within the map's bounds, what occupies it, and if it's a pushable block, is the tile behind it free? If any check fails, the move is rejected. If the block can be pushed, both the block and the player move together.

Small as these rules are, they interact in ways that aren't obvious — pushing a block into another block, against a wall, or off the edge of the map. Getting the order of checks right mattered, and bugs in this layer were often subtle to trace back to their source.

Rules as a Runtime System

Rules are formed when blocks align into a sentence like MEEPO IS YOU or WALL IS STOP. After every move, the game scans the board for these alignments, collects the active rules, and applies them to the world.

This means the rules aren't fixed. Pushing a block out of a sentence disables it; pushing a block into a new sentence activates one. A single move can break one rule and create another at the same time, so the game has to recompute and reapply rules from scratch on every turn rather than caching them once at level load.

Integrating with a Provided GUI

Because the GUI was already written, I had to read through someone else's code, understand its conventions, and build my logic to fit cleanly on top of it. This is very different from writing everything from scratch — it forced me to think about what a module should expose, how to keep my code decoupled from the GUI's internals, and how to reason about code I hadn't designed myself.

Testing with pytest

I used pytest to test the game logic independently of the GUI. Because the rules are dynamic — a sentence isn't just data, it's a change to the rules of the simulation — testing helped me verify that a given arrangement of blocks produced the correct set of active rules without having to play through the level visually.

Reflections

This project was my first real experience with the idea that game logic and game presentation are two separate things — and that the logic is where most of the actual work lives. Once I made that distinction, everything became easier: the GUI could do whatever it wanted, and my job was to expose a clean interface for it to query.

Working with pygame and pytest for the first time also gave me a taste of what a real Python project looks like — a set of libraries, a testing framework, and code that has to integrate with other people's work.
