Writing a Shell from Scratch

Building mysh, a fully functional Unix shell in C — from builtins and environment variables to pipes, background processes, and inter-shell messaging.

January – April 2022 C · Systems Programming · Unix

Overview

In this project, I wrote a C program that implements a fully functional shell. It is one of the largest project I have worked on, and also the one I'm proudest of.

Writing a shell from scratch is a large and daunting task, but I'm glad I had the opportunity to do it. It gave me a much richer understanding of shells and of Unix/Linux systems more broadly — systems that are still widely used in industry today.

The shell is called mysh. Over the course of the project, it grew from a simple command loop into something that could realistically be used as a day-to-day shell.

Features

mysh implements a wide range of shell features:

  • Built-in commands. Commands like echo, wc, and cat are implemented directly within the shell. For commands that don't have a builtin, mysh falls back to Bash's implementation by forking a child process and using exec.
  • Environment variables. Supports an arbitrary number of environment variables, stored in a linked list allocated on the heap.
  • File system management. Implements built-in commands like ls and cd so the shell can navigate and inspect the file system without spawning external processes.
  • Pipes and process control. Supports pipes, and allows users to start processes in both the background and the foreground.
  • Running processes. Tracks active processes in a linked list on the heap, so the shell can manage them across commands.
  • Inter-shell messaging. mysh can start a server in the background and listen for incoming messages, and it can also send messages to other mysh instances that are running a server.

What I Learned

Completing this project gave me experience with:

  • Unix and Linux operating systems
  • Common shell commands and their semantics
  • C programming at a level of real system complexity
  • Error checking and handling
  • Dynamic memory allocation on the heap
  • Working remotely on a different machine using ssh
  • Implementing functionality on a tight weekly schedule
  • Writing well-documented, organized, and extendable code
  • Testing and reasoning about code separately before merging it into the main application
  • Version control with git
  • Writing unit tests with pytest

Reflections

This project was genuinely hard. A shell is not just a program that reads input and executes commands — it's an orchestration layer that has to manage processes, memory, file descriptors, environment state, and error handling simultaneously. Getting all of that to work together, and keeping the code organized enough to extend week after week, was the biggest engineering challenge I've taken on at that time.

What made it rewarding was seeing a project that felt impossible at the start become something I could actually use. By the end, mysh was a real shell — not a toy, but something that behaved the way a shell is supposed to behave. That shift, from "this is too much" to "this works and I understand how it works," is the reason I consider it my proudest project.

It also changed how I think about the tools I use every day. Every time I open a terminal now, I have a much clearer sense of what's happening underneath the prompt.
